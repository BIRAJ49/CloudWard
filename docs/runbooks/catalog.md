# CloudWard runbook catalog

All automation uses typed actions; no runbook embeds a shell command. Every runbook requires fresh structured evidence, exact namespace/label boundaries, deterministic risk, fail-closed OPA, audit, and post-action verification. Production persistent changes remain GitOps- and human-controlled.

| Runbook | Trigger and evidence | Preconditions and risk | Action / approval | Verification, rollback, limitations |
| --- | --- | --- | --- | --- |
| R1 bad deployment | Alert after a staging release; readiness/error metrics, pods/ReplicaSets/events, logs/traces, deployment digest/SHA and diff | Controlled staging Deployment; previous healthy digest proven; current evidence; high confidence. Production raises risk and cannot be a demo target. | Create a draft GitOps revert proposal. Human approval where policy requires; never auto-merge production. | Argo sync, desired/live digest, replicas, health/error signals. Revert PR/commit if validation fails; missing previous digest escalates. |
| R2 CPU saturation | Sustained CPU utilization/throttling plus request/error evidence | Staging demo label, bounded observation, no active conflicting change | Temporary bounded replica increase or reviewed GitOps proposal according to policy; approval follows risk. | CPU/throttling, readiness, latency/errors, replica ownership. Restore original replicas on failed verification; this is not predictive scaling. |
| R3 memory pressure | Working-set/limit pressure, restarts/OOM evidence, workload and event snapshot | Controlled staging target; resource evidence sufficient and current | Reviewable resources PR; no live production memory mutation. | Restart/OOM trend, readiness and application health after GitOps. Revert Git change if degraded; sparse windows block action. |
| R4 workload/platform failure | Unhealthy controller-managed pod or scheduling/capacity symptoms; Deployment, pod, node, Karpenter events | One exact allowlisted target; controller ownership; distinguish CloudWard from Kubernetes/Karpenter recovery | Delete only the unhealthy pod or request bounded capacity as defined by runbook/OPA. Higher risk requires approval. | Ready replicas, pod/application health, node readiness, resolution source. Kubernetes recreates pod; no rollback to the same pod. Three failed attempts escalate. |
| S1 suspicious shell | Authenticated normalized Tetragon process event with pod/image/namespace identity | Staging demo label; policy match; exclude system/production targets | Apply bounded Cilium quarantine after risk/OPA; approval per containment policy. | Prohibited traffic blocked while health/management checks remain observable. Remove quarantine for rollback; sensor blind spots remain. |
| S2 unexpected egress | Tetragon network event to the controlled internal simulator plus identity evidence | Exact staging workload and prohibited destination; dedupe/replay checks pass | Apply namespaced Cilium egress quarantine; audited notification/Issue optional. | Test destination becomes unreachable, permitted service/DNS behavior remains. Remove policy on false positive or collateral impact. |
| S3 privilege behavior | Tetragon privilege/capability event and pod security context/admission evidence | Controlled workload; no host/system target; event authentic and current | Quarantine proposal/action through risk and OPA; higher-risk containment may await Operator/Admin. | Behavior ceases or pod is isolated without cluster-wide effect. Roll back policy if verification harms safe traffic; runtime telemetry is not proof of exploit. |
| F1 workload rightsizing | Prometheus CPU/memory window plus OpenCost allocation for an overprovisioned staging workload | Minimum coverage/sample count; same workload/container; non-stale values; deterministic headroom/floors | Create a reviewable staging values PR. Human review required; never live-patch or auto-merge production. | CI/Helm/admission/staging health and later observed window. Close/revert PR if degraded. Dollar impact is labeled estimate and never fabricated. |
| F2 node capacity | Requested/used capacity, node allocation, Karpenter class and OpenCost evidence | Sufficient window, non-critical workload, bounded families/capacity, On-Demand fallback | Recommendation or draft infrastructure/GitOps PR only; no automatic production/node changes. | Scheduling, node readiness, utilization/cost evidence, disruption behavior. Revert configuration if availability declines; CloudWard does not claim Karpenter consolidation as its remediation. |

Runbook YAML under `runbooks/` is executable source; this catalog is the operator-facing contract. If documentation and the validated schema differ, execution must fail closed until they are reconciled.
